## Audience: Windows out of the box

Starting with 0.3.0, oc targets general Windows users, not only this machine. Staged: Windows first; Linux and macOS are not a requirement yet.

- Works in any Windows terminal: Windows Terminal, the classic console (conhost), WezTerm, and others.
- No hardcoded personal paths, apps, or config in shipped behavior.
- PowerShell 7 (`pwsh`) is a required dependency (decided 2026-10-03). Do not add Windows PowerShell 5.1 fallbacks.
- **Capability tiers, not lowest common denominator.** Build each feature to its full version. Detect what the current terminal supports and give each terminal the best version it can handle. Never cut a feature everywhere because one terminal cannot do part of it.
- Terminal detection happens in one shared helper (env: `WT_SESSION` for Windows Terminal, `TERM_PROGRAM=WezTerm` / `WEZTERM_PANE` for WezTerm, otherwise generic). Features read its result; no per-feature env sniffing.
- Unsupported pieces degrade silently and harmlessly (ignored escape sequences, hidden menu options), never with errors or broken output.

## 2. Sidebar controls show real session state

**Status:** complete (v0.2.78). Rows read `local.model.current()` / `variant.current()`; reasoning row stays visible as `default` when the model has variants. Live check pending.

**Feature:** The `> <model>` and `> <reasoning>` rows at the top of the sidebar always match the current session and the prompt footer. Clicking reasoning updates the row immediately and correctly. Today they can show another session's last choice.

**Cause (confirmed by Grok, Wave 0):** Each row copies a value into local signals from a different source:
- Reasoning (main bug, high): reads the global `model.json` variant for that model, shared by every session and tab, never `local.model.variant` (`sidebarTools.tsx:447-451`, `230-238`).
- Reasoning click: `variant.cycle` is async; the 50 ms file re-read races it (`828-838`; `app.tsx:1401-1406`).
- Model (medium): uses `local.model.current()` first, so it is mostly right. But a failed refresh keeps the previous session's label (`438-441`), and the live path ignores its `forSessionID` argument.
- Reasoning reacts on `onMouseDown`; Switch Session and model use `onMouseUp` (`1595-1619`).

**Implementation:**
- Replace `model`/`variant` signals with reactive reads: `local.model.current()` for the label and `local.model.variant.current()` for reasoning. These already honor per-session overrides and are what the prompt footer uses (`prompt/index.tsx:215,1562,1569`).
- These APIs follow the routed session. The sidebar's `props.sessionID` is the routed session today (`routes/session/index.tsx:1475,1487`), so they match.
- `variant.current()` can be `undefined`; show the same as the footer (hide or "default"), not blank.
- Delete `MODEL_STATE_PATH`, `savedModelState`, `savedVariant`, `refreshSelectedModel`, `refreshVariant`, the 500 ms `setInterval`, the `fs.watch`, and the 50 ms `setTimeout` in `cycleVariant`.
- `cycleVariant` keeps only the dispatch and error toast; switch it to `onMouseUp` like the other rows.
- Result: less code, no polling, cannot drift.

## 3. Usage section fresh and honest

**Status:** complete (v0.2.78). Per-provider refresh after use (45 s throttle, `claude-code-<account>` maps to claude-code), refresh on session select when older than 60 s, stale/cached rows dimmed. No tooltip pattern exists, so no hover age. Live check pending.

**Feature:** Usage numbers update soon after you use a provider, refresh when you return to a session, and never show old or cached numbers as if they were current. Stale or cached rows are dimmed, with "updated Nm ago" on hover (decided).

**Cause (confirmed by Grok, Wave 0):**
- Refresh runs only when the visible session goes idle (`usage.ts:132-137`), plus a 5 minute fallback. Long turns never go idle. Other sessions, Codex CLI, and Cursor IDE use only show up on the fallback. Session switch does not refresh usage.
- Every refresh probes all enabled providers at once (`sidebarTools.tsx:460-481`).
- Only `probeClaudeCodeUsage` passes cache off as live (`usage.ts:235-236`, `249-254`). OpenAI, Go, OpenRouter, and Cursor return `{ ok: false }` on failure, and the UI keeps the last good numbers until the next success, with no age shown.

**Implementation:**
- Track per-provider `{ fetchedAt, source: "live" | "cache" }` alongside each usage result.
- `refreshUsage(providers?)`: probe only the given providers; default all.
- Targeted refresh: subscribe to `message.updated` for usage (today it only drives file/script refresh at `sidebarTools.tsx:1533`). On an assistant message with `time.completed`, map `info.providerID` to its usage row and refresh only that one, throttled to one request per provider per ~45 s. The provider-to-row map is explicit (`openai`, `claude-code`, `opencode-go`, `openrouter`, `cursor`); IDs are not 1:1 (`sdk/js/src/v2/gen/types.gen.ts:337-356`).
- On session select or sidebar becoming visible: refresh providers whose data is older than ~60 s.
- Keep `createUsageRefreshScheduler` and the 5 minute fallback for everything else.
- Claude probe returns `source: "cache"` instead of passing cache off as live. A failed probe for any provider keeps the last numbers but marks them stale.
- Render: dim rows when `source === "cache"` or older than a few minutes; tooltip shows age.

## 6. Questions survive closing the session

**Status:** complete (v0.2.78). Two fix rounds after Grok reviews plus one orchestrator fix. Known limitations: a question answered from a second TUI can still show restored on this one until it reloads; bootstrap still fetches for the attach folder (session open fetches the right one); plugins do not see restored questions; sub-agent rows do not mark restored questions as waiting. Live check pending.

**Feature:** If an agent asks a question and you close the oc window, the question is still there when you reopen the session. Answering it continues the agent. No more asking the agent to re-ask.

- Live question still pending on the server: shown and answered normally.
- Original turn already gone: the question is rebuilt from the saved tool call; your answer is sent as a follow-up message and the agent continues from it.

**Cause (traced by Grok, Wave 0; not yet reproduced live):**
1. Most likely: the question is still pending on the server, but the reopened TUI asks the wrong place. `occ` attaches with `--dir` set to the home folder (`cli/cmd/oc.ts:159-176`), and `question.list` only returns questions for the instance of that directory (`instance-context.ts:28-29`). The TUI calls it once at startup (`sync.tsx:657`) and never on session open (`sync.tsx:780-791`). Missed `question.asked` events are not replayed.
2. After a server restart or instance dispose: pending questions are in memory only, and the finalizer rejects them all (`question/index.ts:75-80`). The tool part becomes `error` but keeps its `input` (`session/processor.ts:191-208`).
3. Claude Code only, long away: the proxy question times out after 30 minutes (`provider/claude-code/proxyDeadline.ts:28-36`).
- Ruled out: closing the TUI does not abort the session or reject questions (`app.tsx:547-552`; abort only on undo). Instances have no idle disposal (`project/instance-store.ts:43`).
- Repro to confirm cause 1: ask a question in a project session, close the window, reopen via `occ`; call `question.list` with the session's directory and confirm it is still there.

**Implementation:**
- Refetch pending questions (and permissions, same bug class) for the session's own directory whenever a session is opened, not just at startup. Per-session `question.refresh` / `permission.refresh` already exist in `context/data.tsx:443-451`; the session UI reads `sync.data.question`, so feed that store.
- Claude Code: let the proxy question wait as long as oc's own question (no 30 minute cutoff), or turn a timeout into the restored-question path.
- If nothing is live but the session's latest `question` tool part ended unanswered (error from rejection, or `running` with no live request), rebuild the prompt from the part's saved input. Mark it as a restored question.
- Answering a restored question sends a normal user message in the same answer format the tool returns (`"question"="answer"`), so the agent sees it exactly like a tool result.
- Dismissing it clears it.
- No schema change.

## 8. Revive closes only oc's own terminal windows

**Status:** complete (v0.2.78). Per-TUI ledger in the state dir, resolved executable identity across oc/occ/opencode hard links, one CIM listing via pwsh, `wezterm cli kill-pane` for WezTerm panes, production leaves ocdebug alone. Known limitations: first revive after upgrade may leave pre-ledger TUIs open; a force-killed TUI cannot clear its tab progress ring; if process listing fails, TUIs stay open but the server still stops. Live check pending.

**Feature:** Revive and `--shutdown-all` close only the terminals running oc. Your other terminal windows stay open, in any terminal.

| Terminal | Behavior |
|---|---|
| WezTerm | Closes exactly the panes that hosted oc (`wezterm cli kill-pane`) |
| Windows Terminal, conhost, others | Stops the oc processes only. A tab or window that was started for oc closes by itself when oc exits; one where oc ran inside a shell drops back to that shell |

**Cause (traced by Grok, Wave 0):**
- Every WezTerm window is killed twice: first by the TUI right after launching the revive helper (`app.tsx:358-359`), then by the helper's `oc --shutdown-all` (`config/oc.ts:420`, no platform guard).
- `shutdownAll` also always stops `ocdebug` (server and TUIs) and any process named `opencode.exe`, including stock OpenCode (`config/oc.ts:337-340`, `410`).
- Killing only oc processes closes a Windows Terminal or console tab that was opened for oc (the `occ` shortcut runs `occ.exe` directly), but leaves an empty pane in WezTerm. Hence `kill-pane` for WezTerm.
- `WT_SESSION` identifies a Windows Terminal window, not a tab, so it cannot target one tab. Not needed: killing the oc process closes the tab.

## Orchestration

Claude Code orchestrates. Workers are headless `oc run` sessions on the `build` agent with a chosen model and reasoning level. The orchestrator writes prompts, monitors, verifies, merges results, and owns build notes and version bumps.

### Driving workers (verified 2026-10-03)

```powershell
oc run --dir <repo> --agent build -m <provider/model> --variant <level> --title "v030/<item>/<role>" --format json "<prompt>" > <log>.jsonl
oc run --dir <repo> -s <sessionID> --format json "<follow-up>"   # continue the same worker
```

- Subagent-mode agents cannot be primary in `oc run` (falls back to default), so role and model come from flags plus the prompt, using the subagent definitions as the role guide.
- Standalone `oc run` starts its own local server; no resident-server secret needed. Sessions land in the shared database, so they show up in the TUI session list under their `v030/...` titles.
- Baseline cost: ~33k input tokens per fresh session (system prompt). Continue with `-s` for follow-ups to reuse context and cache.
- Run each worker in the background; read only the result when it finishes.

**Monitoring:** JSON events are one per line: `step_start`, `tool_use` (`part.tool`, `part.state.status`), `text` (`part.text`), `step_finish` (`part.reason`, `part.tokens`). A small scratch summarizer prints tool count, errors, token total, and the final `text`. Full logs are read only on failure.

**Session tools:** workers call `session_in_progress` at start and `session_complete` / `session_failed` at the end, so status is visible in the TUI. Run with `--auto` only for edit workers whose prompt fixes the file allowlist.

### Roster

| Role | Model / flags | Use for |
|---|---|---|
| Implementer | `openai/gpt-6.1-sol --variant low` | Core items: minimal root-cause fixes, precise research, self-verification |
| Implementer, heavy | `openai/gpt-6.1-sol --variant medium` | Larger end-to-end pieces needing production-grade completion (items 6, 11c) |
| Grunt | `cursor/composer-2.5` | Mechanical, bounded, easy-to-verify jobs: line-ref refresh, greps, renames, small config, test scaffolds |
| Grunt, smarter | `opencode/muse-spark-1.3-contributor-free` (free) | Small well-specified edits with a little judgment; used generously |
| Bug finder | `cursor/grok-4.6 --variant low` | Repro analysis, root-cause hunting, diff review, red-team. Read-only: reports findings with file:line, never writes the fix |

### Shared worker preamble

Every prompt starts with the same block (scratch file, pasted in):
- Repo rules: follow `AGENTS.md`; smart, simple, efficient code; fix shared paths.
- Never build, install, push, or touch files outside the given allowlist. Leave unrelated worktree changes alone.
- Only run the checks named in the prompt.
- End with: files changed, what was verified, what was not.
- Grok prompts add: read-only, cite file:line for every finding, rank by severity, no fix code.

### Patterns

1. **Scout first, cheap.** Before each wave, Composer/Muse workers re-verify the plan's line references and gather caller lists for their item. Results update this file.
2. **Grok finds, Sol fixes.** For bug items (2, 3, 6, 8), Grok runs first to confirm the cause with citations. Its report becomes the Sol implementer's brief.
3. **Review gate.** Every Sol change gets a Grok diff review (`git diff -- <allowlist>`). Findings go back to the same Sol session via `-s`, never to Grok to fix. Max two loops, then the orchestrator steps in.
4. **Independent tests.** For logic with a clear spec (nearest emoji square, editor resolution, usage throttle, terminal detection), a Muse worker writes tests from the spec alone, without seeing the implementation. If they disagree, the spec or code is wrong.
5. **Two-angle review on risky items.** Items 6 and 11c get two Grok passes: correctness, and Windows terminal edge cases (Windows Terminal, conhost, WezTerm).
6. **Disjoint parallelism.** Workers in the same wave get non-overlapping file allowlists in the one checkout. Items touching the same file (2 and 3: `sidebarTools.tsx`) run in sequence in one Sol session.
7. **Orchestrator verifies.** After each item: read the diff, run the item's targeted tests, `tsc --noEmit` for the touched package, update the item's status here.
