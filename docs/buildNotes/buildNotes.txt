v0.2.361 jakeTimtam [fix > warm-up errors and damaged store]

Claude warm-up:
When saving a warm-up schedule fails, the dialog now shows the real reason instead of always saying "Warm-up inventory unavailable".

A damaged warm-up schedule file no longer hides every account. If one account's entry cannot be read, only that account shows as not configured, the dialog names it, and the other accounts keep sending; saving that account's schedule replaces the entry. If the whole file cannot be read, warm-ups stop and the dialog says so; saving any schedule starts a new file and keeps the old one beside it as warmup.json.bad. A file that is only locked or not permitted is never touched.

Saving a schedule no longer shortens an account's palette name when two account folders share the same name.

Under the hood: the warm-up store now tells I/O failures apart from bad content, keeps unreadable entries untouched on every write, and removes its temp file when a write fails. The scheduler counts only due accounts as skipped when the Claude CLI is missing, the attempt-recording code and the Claude CLI path lookup are no longer copied in several places, and a few small TUI cleanups landed (time-limit message, reset math, preset sorting). Tests: the store test now checks the new recovery contract, and two stale global API tests were corrected (dotless account labels, a real I/O failure for the save-error case). Checks: core, opencode, and tui typecheck clean; opencode warm-up and global API tests 58 pass; tui warm-up tests 28 pass; probes against the real handler confirmed the damaged-file and bad-entry recovery. Not checked: the live TUI dialog.
